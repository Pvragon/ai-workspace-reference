# Progressive Disclosure Convention

> This convention improves context window efficiency by adding a `summary` frontmatter field to all agent-consumable files and evolving index files into aggregated discovery tables. Agents can scan summaries to assess file relevance before committing to a full read. The only file receiving an exec summary blockquote is `workspace-reference.md` (464 lines); all other files rely on the frontmatter field alone.

## The `summary` Frontmatter Field

All agent-consumable files over 15 lines MUST include a `summary` field in their YAML frontmatter. This is a required field alongside `template`, `version`, `created`, `last_updated`, and `maintainer`.

```yaml
---
template: [type]
version: [semver]
summary: "What this file is and when an agent needs it."
created: [YYYY-MM-DD]
last_updated: [YYYY-MM-DD]
maintainer: [team/person]
---
```

### Writing Guidelines

The `summary` field answers exactly one question: **"Should I open this file?"**

- 1-2 sentences maximum
- Name the concrete thing (not "this document covers..." but "Defines the execution script standard...")
- State the when/why ("Load when building new execution scripts.")
- Tool-agnostic (valid for Claude, Gemini, and future AI tools)
- Update the summary when bumping the file version

### Good Examples

- `"Canonical reference for workspace architecture, directory conventions, and agent operating rules. Load when an agent needs to understand where something belongs."`
- `"Procedure for graduating files from my-lib to team-lib. Follow when a local tool is ready for team-wide use."`
- `"Your brand guidelines: colors, typography, logo usage, and document formatting. Required before generating any branded deliverable."`

### Bad Examples

- `"This document is about the workspace."` (too vague, no decision signal)
- `"Important information about various topics."` (useless)
- `"A comprehensive guide that covers many important topics related to the AI Workspace architecture and its various components."` (verbose, no decision signal)

## Reference Files vs. Instruction Files

Both file types get the `summary` field, but agents use it differently.

**Reference files** (context/indexed/, business overviews, framework definitions): Agents use `summary` to decide whether to open the file. Partial reads are legitimate.

**Instruction files** (AGENTS.md, SKILL.md, directives, personas): Agents use `summary` for discovery ("which skill do I need?"), but once opened, they read the file in full. Every word matters. The `summary` never substitutes for reading the file.

## Skill Listing (the harness layer)

Skills have one more disclosure layer than other files, because the harness itself announces them. Claude Code shows the model a skill list every session, but drops descriptions once the list passes about 1% of the context window, least-recently-used first. So each skill states how it is listed instead of competing for that budget:

- **`listing`** (`on` / `name-only` / `user-only`) decides whether the harness announces the skill with its description, by name only, or not at all (it then runs only when the user types `/<name>`). It is rendered into Claude Code's `skillOverrides` by `build_skill_overrides.py`.
- **`category`** is the facet `find-skill` filters on, one name from `team-lib/config/skill-categories.yaml`. Personas declare `skill_categories` and pass them to find-skill when they load.
- **`summary` / `description`** is what `find-skill` searches, so the discovery guidance above applies to skills twice: once for the index, once for the search.
- **Third-party skills** under `_external/` must not be edited, so they never carry these fields in their own files. They take `listing` and `category` from the sidecar `team-lib/config/skill-listing.yaml` (personal overrides: `my-lib/config/skill-listing.yaml`), or the external default `user-only`.

## Index File Aggregation Pattern

Index files (`index.md` in each directory) aggregate the `summary` fields from their sibling files into a discovery table, so an agent can scan one file to assess all siblings without opening any of them.

**The table is GENERATED, never hand-written** (since 2026-08-08). It lives under a `## Contents` heading and is produced by `team-lib/executions/build_index.py` from the same `config/registry-map.yaml` that drives the registry manifest — so the index and the manifest cannot disagree about which files exist or what they say.

```markdown
## Contents

<!-- GENERATED by team-lib/executions/build_index.py from each file's `summary:` — do not
     hand-edit. To change a row, edit the `summary:` in the file that row names. -->

| Name | Summary |
|------|---------|
| [`filename`](filename.md) | [summary from that file's frontmatter] |

See [`registry/context.yaml`](../../registry/context.yaml) for the full manifest.
```

Four rules follow from it being a build artifact:

- **To change a row, edit the `summary:` in the file it names.** An edit to the table is discarded on the next run, and believed in the meantime.
- **Everything OUTSIDE `## Contents` is yours.** Purpose / What Belongs Here / naming conventions are hand-authored and preserved byte-for-byte. If `## Contents` contains anything the generator could not have written, it REFUSES rather than overwriting — move that text to its own section.
- **`summary:` owns a row; `description:` is a reported fallback.** Files carrying only `description:` (chiefly third-party skills under `_external/`, which must not be modified) are listed from that field and reported, never silently substituted.
- **A file with no pointer field still gets a row**, marked as missing. An index narrower than the directory it indexes reads as coverage.

Run it with `build_index.py --repo <REPO>` (read-only rebuild-and-diff) or `--apply`. It also runs automatically at the push boundary via `version_gate.py`, alongside the manifest rebuild.

## Exempt Files

The following do not need a `summary` field:

- Files under 15 lines (e.g., CLAUDE.md/GEMINI.md stubs, workspace root AGENTS.md)
- Third-party files in `_external/` directories (must not be modified)
- CHANGELOG.md, README.md in project roots
- Registry YAML files (use comment-block summaries instead)

## Registry YAML Convention

YAML registry files use a comment-block summary at the top of the file:

```yaml
# summary: One-sentence description of what this registry covers.
# last_updated: YYYY-MM-DD
# entries: N
```

The header comment block is hand-authored and preserved by `build_registry.py`; the entries below it are generated. Derived fields, by manifest:

| Manifest | Derived (owned by the file; never hand-edit) |
|---|---|
| `skills.yaml` | `path`, `version`, `description` (from `summary:`), `source` (provenance: local / team / external / project / system / synced), team-lib's `provider`, and **`listing`** and **`category`** (frontmatter, then sidecars, then the provenance default) |
| `personas.yaml` | `path`, `version`, `description`, my-lib's `source`, and **`skill_categories`** (vocabulary-checked) |
| others | `path`, `version`, `description` (+ `source` where the registry-map says so) |

Any other field in an entry (`tags`, `traits`, `use_cases`, notes) is hand-authored and preserved.

## Future Expansion

If practice reveals specific large files (200+ lines) that would benefit from an exec summary blockquote after the H1 title, they can be added individually. The current exception is `workspace-reference.md` only.
